先看整条主线

这次请求没有自己的路由登记。数据面 create_router_app_with_route_miss() 把 /v1/chat/completions 和其它没单独登记的路径一起交给 .fallback(proxy_handler)。这是有意的设计。

trust 领域不在这九步里。它的唯一 crate 是本地推理进程管理，只被 burncloud-service 依赖，而 burncloud-service 没有被任何 crate 依赖。这一点是直读。到 L1 看 trust。

01 程序入口

路径与函数

  • crates/interfaces/cli/src/main.rs · main()
  • 根 Cargo.toml 的 [[bin]] name = "burncloud" 指向这个文件。
  • run_async_server()：burncloud server 和 burncloud router 两个子命令都会调用它。
  • 读取环境变量 HOST、PORT 后调用 burncloud_server::start_server(&host, port, true)。
  • 不带参数时：Windows / macOS 在后台起 server，并打开桌面 GUI（burncloud_client::launch_gui_with_tray()）；Linux 走无界面的 LiveView server。
  • ensure_runtime_secrets() 生成 MASTER_KEY、JWT_SECRET、BURNCLOUD_INTERNAL_SECRET，并写进 .env。
  • 默认地址：HOST 默认 127.0.0.1（main.rs）；PORT 默认 3000（crates/interfaces/common/src/constants.rs 的 DEFAULT_PORT）。

03 HTTP 路由注册

Server 层

同一个文件里的 create_app_with_node_request_state，按这个顺序挂载：

  1. /health
  2. 管理 API api::routes（/console/api/{*path}）
  3. model_selection::routes()（/api/models/presets|search|status）
  4. 内部路由
  5. LiveView 控制台 burncloud_client::liveview_router（/console）
  6. fallback_service(router_app)，其余请求交给数据面

全局还有一层 api::auth::security_boundary_middleware（crates/interfaces/server/src/api/auth.rs）。注释写明：控制台 JWT 不能当推理凭证用；敏感的内部 POST 必须带 BURNCLOUD_INTERNAL_SECRET。

数据面

crates/traffic/router/src/lib.rs · create_router_app_with_route_miss() 登记了：

  • /v1/models
  • /api/v1/usage
  • /api/v1/usage/models
  • /console/internal/health
  • /console/internal/prices/sync
  • /console/internal/circuit-breaker/trip-all

其余路径，包括 /v1/chat/completions，都走 .fallback(proxy_handler)。代码里没有单独为 chat/completions 注册的路由。

04 鉴权

  • crates/traffic/router/src/lib.rs · proxy_handler()
  • 依次从 Authorization: Bearer、x-api-key、x-goog-api-key 取 token，取不到就返回 401。
  • 然后调用 RouterDatabase::validate_token_and_get_info（crates/traffic/router/src/storage/mod.rs），内部转调 burncloud_identity_token::TokenService::active_api_key_identity。
  • 查不到时退回 validate_token_detailed，旧 token 表还会尝试 JWT 校验。

直读

05 计费预检

  • crates/traffic/router/src/lib.rs · proxy_logic() 内的 state.cost_calculator.preflight(model, None)
  • CostCalculator 来自 burncloud_commerce_billing。
  • 严格模式下查不到价格直接返回 400；非严格模式只打警告（见 create_router_app_with_route_miss 里的注释）。

直读

06 路由 / 选上游

  • proxy_logic() 调用 state.model_router.route_for_dispatch(RouteInputs{..})（crates/traffic/router/src/model_router.rs），里面再调 route_with_scheduler()。
  • 调度分为 strict 和 legacy。相关模块：crates/traffic/router/src/scheduler/（strict / passthrough / combined）和 balancer/。
  • 候选渠道通过 burncloud_supply_channel::ChannelService 查 channel_abilities。代码注释原话：Supply 拥有查询，Traffic 拥有路由决策。
  • 没有候选时，调用 server 注入的 route_miss_responder → crates/interfaces/server/src/node_request.rs · route_miss_response()。如果本机 Node 正在准备这个模型，返回 “model preparing”。

直读

07 适配器 + 调上游

proxy_logic() 按 upstream.protocol 把请求映射成 ChannelType（claude / gemini / vertex / zai，其余按 OpenAI 处理）。有两条发往上游的路径：

  • 透传：passthrough.rs，比如 build_gemini_passthrough_url。
  • 转换：state.adaptor_factory.get_adaptor(...)。适配器在 crates/traffic/router/src/adaptor/（claude / gemini / vertex / zai / dynamic / factory）。

两条路径都由 reqwest 的 req_builder.send() 发出。失败时走重试、熔断和 failover，相关文件是 circuit_breaker.rs、smart_circuit_breaker.rs、channel_health_manager.rs。

本机节点是另一条旁支，见下方虚线卡片，不和上游模型画成同一条已接通的箭头。

直读

网关侧的发送点：passthrough.rs（例如 build_gemini_passthrough_url）和 crates/traffic/router/src/adaptor/。两条都由 reqwest 的 req_builder.send() 发出。

协议映射：claude / gemini / vertex / zai，其余按 OpenAI。
