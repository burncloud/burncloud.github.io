这一层看的是 Cargo.toml 里的普通依赖，不是一次请求的先后顺序。箭头从依赖方指向被依赖方。点领域或编号，看支撑这条边的 crate；完整名单在图下面，不靠悬停。

  • 实线：普通依赖
  • 虚线：反向，traffic 依赖 interfaces/common
  • 点线，编号是圆的：只依赖契约 crate
  • trust 用虚线框，不在当前请求主线上
  • 交叉的地方线会断开，表示穿过，不是接在一起

屏幕较窄时不画连线，避免编号和领域名叠在一起。依赖关系在下方的表里，逐条写了支撑的 crate。

宽屏上的编号和表里的编号是同一条边。上下方向键在领域之间移动。Esc 回到总览。

先看分工，再看箭头

上排 interfaces 是入口。中间四个领域里，traffic 的 router 是依赖最多的枢纽：它直接依赖 identity、supply、commerce、platform，以及 interfaces 里的 common。这条 common 边是反向的，在图上用虚线单独画出来。

platform 在最下面，没有指向其他领域的普通依赖。burncloud-database 的 Cargo.toml 注释写明它刻意不依赖 identity-user / supply-channel，并由 deny.toml 强制禁止。

trust 画在旁边：唯一的 crate 管本地推理进程，只被 burncloud-service 依赖，而 burncloud-service 没有被任何 crate 依赖。当前请求主线上看不到它。这一点是直读。回 L0 看那一次请求。

素材这一层按 crate 和 Cargo.toml 依赖来写，没有给每个领域单独的函数名。请求主线上点过名的函数，写在各领域说明里，并链回 L0。
