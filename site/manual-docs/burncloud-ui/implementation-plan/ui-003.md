# UI-003：建立 Production Shell 与 Role/Auth Workspace

## 第一层：人类阅读区（Human Readable Layer）

**状态：PLANNED**  
**类别：Foundation**  
**功能依赖：UI-001、UI-002**

> 本页只定义 Shell/Workspace。Buyer、Supplier、Admin 页面内容由各自计划负责。

### TL;DR

把当前以 Providers / Models / Routes 为中心的 Console Shell 改造成 Buyer / Supplier / Admin workspace，但 Role 只能来自后端已授权角色。Role Switcher 是“切换已授权视图”，不是“获得权限”。

### 背景与动机（Why）

当前 Dioxus 已有单一 Router、AuthGate、Sidebar/Topbar，但 product mental model 仍偏内部对象。如果直接逐页改内容而不先建立 Role Workspace，新旧 IA 会长期混杂，并容易把导航隐藏误当成授权。

### 范围速览（In / Out）

| ✅ 做 | ❌ 不做 |
| --- | --- |
| Buyer/Supplier/Admin workspace shell | 不实现具体页面业务 |
| 使用 backend `roles` | 不在前端定义权限 |
| Sidebar/Topbar/Search 随 workspace 切换 | 不删旧 routes |
| 保持 Desktop/Web/LiveView | 不创建第二 Router |

### 风险与安全网（Risk）

最高风险是 client-side role escalation。任何 unknown role 都不得 fallback Admin。

### 审批者关注点（Reviewer Focus）
1. backend authorization 是否始终是最终真相？
2. 多角色切换是否完整切换 Sidebar/Overview/Search scope？
3. 旧 deep links 是否先兼容、后单独退役？

## 第二层：机器执行层（Machine Executable Specification）

### 1. Goal

建立一个生产 Dioxus Role Workspace Shell：只在 backend-authorized roles 中选择 Buyer/Supplier/Admin workspace，并保持 single Router/Frontend。

### 2. Evidence

- STATIC CONFIRMED — `app.rs` 是当前 Route source。
- STATIC CONFIRMED — `functional_layout.rs` 拥有 Sidebar/Topbar/search。
- STATIC CONFIRMED — `AuthContext::CurrentUser` 已包含 `roles: Vec<String>`。
- STATIC CONFIRMED — `AuthGate` 当前只检查 authentication。
- STATIC CONFIRMED — 现有 Sidebar 仍暴露 Providers/Models/Routes mental model。
- UNKNOWN — current-main canonical backend role vocabulary；Task Contract 必须重新确认。

### 3. Entry / Starting Point

```text
crates/client/src/app.rs
crates/client/src/functional_layout.rs
crates/client/src/auth_gate.rs
crates/client/src/backend.rs :: CurrentUser/AuthContext
backend role/authorization tests
```

### 4. Reuse Targets / Do Not Recreate

Reuse：existing Router/AuthGate/AuthContext/Sidebar/Topbar/Search/Desktop chrome。  
Do Not Recreate：second Router、second auth shell、client role DB、React frontend。

### 5. Scope

Allowed：Route/Shell/Auth workspace state、compatibility aliases needed to preserve current behavior、targeted tests。  
Avoid：page business implementation、backend role mutation、route deletion、billing/routing changes。

### 6. Behavior Contract

**Inputs**：authenticated user roles、current/requested workspace。  
**Outputs**：active authorized workspace + corresponding Sidebar/title/search scope。  
**Ownership**：backend grants roles；Shell only selects/presents granted roles。  
**Side Effects**：navigation/workspace state only。

### 7. Failure / Forbidden Fallbacks

Unknown/no supported role → explicit unavailable state。Auth missing → existing login redirect。禁止从 username/URL/localStorage/query 推断 Admin/Supplier；禁止隐藏 route 作为 authorization。

### 8. Impact / Invariants

```text
persistence: none expected
external_calls: no new business calls
auth_authorization: presentation consumes backend roles only
frontend_navigation: yes
```

保持：backend authorization final truth；one Dioxus Router；legacy route compatibility；workspace switch 不授予权限。

### 9. Dependencies

必须在 UI-001、UI-002 稳定后进入 READY。实现前重新确认 backend role vocabulary/test coverage。

### 10. Stop Conditions

```text
STOP IF:
- backend lacks stable role/capability facts
- shell requires server authorization semantic changes
- implementation requires deleting legacy routes
- page-specific backend/data behavior must be bundled
- second Router/frontend is proposed
- Desktop/Web/LiveView compatibility cannot be preserved
```
