UI-001：建立 Target Standard → Production Contract

第一层：人类阅读区（Human Readable Layer）​

状态：PLANNED
类别：Foundation
功能依赖：无

这是实施计划，不是 Codex 的直接开发授权。实现前必须针对当时 burncloud/burncloud/main 重新做 Evidence Audit，并创建通过 READY Gate 的 Engineering Issue。

TL;DR​

先把“目标产品标准”和“当前生产事实”的边界写死，让后续所有 UI 工作都知道什么可以作为产品要求、什么必须从 current main 取证。UI-001 不改用户可见导航，也不实现任何 Buyer / Supplier / Admin 页面。

背景与动机（Why）​

BurnCloud 同时存在批准后的 UI Target、现有 Dioxus Console、历史页面和 Workbench。若没有一层明确的 Production Contract，Agent 很容易把 mock、截图或旧页面行为当成生产事实，最终形成第二套 source of truth。

范围速览（In / Out）​

✅ 做❌ 不做
定义 Target truth / Current truth 边界不迁移 Sidebar/Role Workspace
映射目标 Role/Page ownership不实现具体页面
固定 mock / Unknown 规则不改 Backend API / schema
给后续 Issue 提供统一引用点不复制 Target 文档成为第二权威

风险与安全网（Risk）​

这是低风险合同层改动。若实现需要改变页面行为、backend 或复制产品标准，必须停止，而不是把“合同任务”扩大成重构。

审批者关注点（Reviewer Focus）​

  1. 是否同意 Target Product Contract 与 current source evidence 严格分离？
  2. 是否同意 production mock / screenshot 永远不是事实源？
  3. 是否同意本 Issue 不产生用户可见功能变化？

第二层：机器执行层（Machine Executable Specification）​

1. Goal​

建立一个生产侧可审计的 Target → Current Contract adapter，使后续 UI Issue 能同时引用批准的目标语义和真实 current-main entry，而不复制产品 source of truth。

2. Evidence​

Evidence baseline：burncloud/burncloud@c314bff9646f9113c9a58a818552fc80c77543a6。

  • STATIC CONFIRMED — production frontend 在 crates/client/src/，使用 Dioxus。
  • STATIC CONFIRMED — app.rs 和 functional_layout.rs 持有现有 route/shell。
  • STATIC CONFIRMED — docs/ui/* 已有 source-derived UI engineering rules。
  • STATIC CONFIRMED — target UI 文档定义 Buyer / Supplier / Admin mental model。
  • STATIC CONFIRMED — Workbench mock、截图和历史页面不能成为生产业务真相。
  • UNKNOWN — 最小 Rust/Docs 表达形式；实现阶段根据 current main 决定。

3. Entry / Starting Point​

crates/client/src/app.rs
crates/client/src/functional_layout.rs
docs/ui/README.md
docs/ui/system.md
docs/ui/pages.md
burncloud.github.io/burncloud-ui/*

4. Reuse Targets / Do Not Recreate​

Reuse：现有 Dioxus Route、authenticated shell、docs/ui/*、现有 UI check scripts。

Do Not Recreate：React production client、第二个 Router、Target docs 副本、production mock registry。

5. Scope​

Allowed：docs/ui/* contract adapter、必要的静态 ownership metadata、现有检查脚本/测试。

Avoid：可见导航、UI-002 visual work、UI-003 role shell、具体页面、backend/API/schema。

6. Behavior Contract​

Inputs：批准 UI Target、current Dioxus route/page/source evidence。
Outputs：可供后续 Issue/Reviewer 使用的单一 contract/ownership mapping。
Ownership：Target docs 拥有产品语义；burncloud/burncloud 拥有当前实现事实。
Side Effects：仅文档/静态合同/检查，不改变 runtime 行为。

7. Failure / Forbidden Fallbacks​

冲突或缺失语义必须记为 UNKNOWN。禁止复制 Workbench mock、添加第二前端、把旧 Providers/Models/Routes 自动解释成新 Role IA。

8. Impact / Invariants​

persistence: none
external_calls: none
billing_usage_quota: none
auth_authorization: none
routing_provider: none
public_api_cli: none
process_runtime_lifecycle: none
frontend_architecture: contract boundary only

保持：one production Dioxus frontend；Target truth ≠ Current truth；Unknown ≠ fact。

9. Dependencies​

功能依赖：无。UI-003 和页面迁移依赖本合同稳定存在。

10. Stop Conditions​

STOP IF:
- current source disproves single-Dioxus ownership
- implementation requires visible navigation changes
- Target Product/Page Contracts must be duplicated as second authority
- backend/API/schema changes are required
- checks cannot meaningfully distinguish mock truth from approved/current truth

第三层：验收层（Definition of Done）​

✅ 功能结果​

  • Target truth / Current truth 边界明确。
  • Buyer / Supplier / Admin 页面 ownership 可被后续 Issue 唯一引用。
  • mock / screenshot / AI assumption 不会被提升为生产事实。

✅ 边界保护​

  • 未创建第二 frontend / Router。
  • 未复制 Target docs 成为第二 source of truth。
  • 未迁移任何用户可见页面或导航。

✅ 回归与验证​

  • 当前 Route / Sidebar 行为不变。
  • 现有 UI convention / functional / product / visual gates 仍可执行。
  • Contract 冲突能输出明确 UNKNOWN/Stop，而不是猜测。

✅ 工程流程​

  • 实现前重新 Evidence Audit current main。
  • Engineering Issue 通过 READY Gate。
  • 生成 Task Contract。
  • 通过 branch + Pull Request 合并。
