**PR 说明摘要：** ## S0-13 — Unhealthy -&gt; detach -&gt; recover safety wiring Adds the reverse safety rail for a local Node route after it has become routable. Framework flow: `Routable -> BecameUnhealthy -> Unhealthy/non-serving -> detach exact existing-router attachment -> DetachedRoute receipt -> retry -> Starting` The application seam now returns a `DetachedRoute` proof only after Traffic's detach side effect succeeds. Recovery requires that proof, preventing callers from accidentally starting the recovery/reattach path when the old route was never removed. Tests prove: - successful attach is required for Routable; - failed attach stays Ready/non-serving; - unhealthy immediately becomes non-serving before detach; - successful detach creates the receipt needed to recover; - failed detach stays Unhealthy and produces no recovery receipt. ### Boundary - No second router or routing truth. - The seam remains generic; production supplies the existing-router attachment/detachment adapter. - No real health/process implementation. - This does not yet solve Traffic-level atomic quarantine if database detachment itself fails; that remains an explicit fail-closed integration concern for the real Traffic adapter. ### Next S0-14: application-level Fake E2E driven only by `ModelDemand`, proving the orchestrator can traverse preparation, route attachment, unhealthy detachment, recovery, and reattachment without…
