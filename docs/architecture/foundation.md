# 基础规则

基础规则只保存所有目录共同需要的稳定要求，不能放 UI、Database、Download 等具体细节。

原来的 [`/architecture/base-rules/`](./base-rules.md) 与本页曾经各写一份正文。具体条款已并入本页，旧地址只保留指向这里的入口。

## 规则继承与优先级

规则按目录逐级继承：基础规则 → 可复用规则 → 一级领域规则 → crate 规则 → 有独立职责的子目录规则。

执行时的权威顺序是：业务 Owner 的服务端事实 → 基础规则 → 可复用规则 → 目录规则 → Issue 修改范围 → 代码。下层不能以实现方便为理由推翻上层。

- 下级只补充差异，不复制上级全文。
- 下级可以增加限制，不能悄悄取消上级规则。
- 可复用规则与业务规则冲突时，以更具体的业务规则为准，但必须明确写出原因。
- 当前代码、临时实现和 AI 的方便不能推翻已经确定的规则。
- 同一规则只能有一个正文位置，其他页面只能引用。

## 1. 目录与职责

- 每段代码必须有明确职责和唯一归属，不允许同一业务散落在多个技术目录。目录同时写清楚“谁负责”“负责什么”和“不负责什么”。
- 外部优先按领域和功能组织，内部实现再按技术需要组织。
- 默认保持目录浅；只有出现真实独立职责时才增加层级。
- `common`、`shared`、`utils`、`helpers`、`misc` 不能成为无边界的垃圾桶。不知道归属时先停止，不得把代码扔进这些目录。
- 目录不等于 crate。默认先做 module；只有边界需要编译器隔离时才升级为 crate。
- 独立 Ownership、独立依赖控制、稳定 Public API、实现隐藏、编译/测试隔离或独立变化速度，才是拆 crate 的理由。文件多、行数多不是理由。

## 2. 领域边界

- 一个业务只能有一个主要 Owner，一个家。一个业务概念、业务状态和数据也只有一个主要 Owner。
- Owner 负责自己的业务规则、状态、Repository、数据表、缓存、事件和测试。
- 其他领域不得直接进入 Owner 的内部实现，不能重新计算、重新保存或修改同一份业务真相。
- 不复制其他领域的业务规则；需要能力时通过其公开契约协作。

> **谁拥有业务，谁拥有数据。**

## 3. 模块依赖

- 依赖必须显式、单向、无环。
- 跨模块只能依赖对方公开边界，不依赖 `internal`、`adapters`、Repository 实现或数据库细节。
- 不允许为了方便形成双向依赖。
- 业务模块不得偷偷创建其他模块的内部 Adapter；跨模块装配由 Composition Root 完成。
- 新增跨模块依赖时，必须能说明为什么由调用方依赖被调用方。

## 4. 公开契约

领域之间通过公开契约协作。同步用 Public API、Contract、Port、Command 或 Query；异步用 Public Event。每个 crate 必须写清楚它对外提供什么、返回什么、失败是什么样以及如何保持兼容。

- 默认 private，按需 public。公开契约只暴露完成当前事情需要的最小内容。
- Public Contract 必须小、稳定、表达业务含义。
- 不得公开数据库 Row、ORM Model、内部 Config、具体 Adapter 或 Repository 实现。
- 已被其他模块依赖的公开契约不能随意破坏；修改时必须识别调用方并给出迁移方式。

## 5. 基础代码规范

- 优先简单、清晰、直接的实现，不为了“架构感”制造抽象。没有真实需要时不提前增加层级、Trait、Factory 或通用框架。
- 一个函数、类型、模块应有清楚职责；发现两个独立职责时再拆分。
- 有真实多实现、替换、隔离或边界需求时才抽 Trait 或接口。
- 避免隐藏副作用和全局可变状态。
- 注释解释“为什么”，不要重复代码已经表达的“做什么”。
- 新增第三方依赖必须有明确用途，避免重复引入同类能力。
- `unsafe` 默认禁止；确有必要时必须说明安全不变量和边界。
- 生产路径不得用 `unwrap` 或 `expect` 掩盖可发生的失败。

## 6. 基础错误处理

- 失败必须显式返回并保留有用原因。不吞错误，不把失败伪装成成功，不用崩溃代替正常错误处理。
- 错误应保留足够上下文，但对外不得泄露内部实现、密钥或敏感数据。
- 业务错误和基础设施错误要能区分。
- Timeout、Retry、Fallback 必须是明确设计，不由底层代码无限重试。
- 只有调用方有能力处理的错误才向上传递；需要转换时保留原始原因。

## 7. 基础日志规范

日志只记录重要入口、出口、状态变化和失败。日志必须能定位事情，但不能记录密码、Token、密钥或不必要的敏感内容。

- 日志用于定位运行问题，不代替业务状态、审计记录或领域事件。
- 日志必须能说明发生了什么、作用对象是什么、结果是什么；避免无意义和重复刷屏。
- 禁止记录密码、Secret、Token、Credential、完整 Authorization Header 等敏感信息。
- 错误日志应保留必要上下文，但不能泄露租户或用户不应看到的数据。
- 同一个错误原则上只在最有处理价值的一层记录，避免层层重复打印。

## 8. 基础测试原则

修改什么行为，就验证什么行为。Bug 修复必须留下回归测试。具体测试方法由对应 crate 和可复用规则决定。

测试跟随代码 Ownership：

```text
源码内 #[cfg(test)]  → 单元测试
crate/tests/          → 本 crate 的公开行为与集成测试
领域 tests/           → 必要的领域内跨 crate 测试
根 /tests/            → 跨领域、E2E、兼容性、系统性能测试
```

- 行为发生变化时必须有对应测试，或明确说明为什么无法测试。
- 优先测试公开行为和稳定契约，不把测试绑死在内部实现细节上。
- 跨模块测试不能成为绕过 Public API 的理由。
- 下级 crate 可以增加更严格的测试要求，但不重复本节。

## 9. 安全底线

- 默认拒绝、最小权限、最少暴露。默认不允许，明确授权后才允许。
- 所有外部输入必须在可信边界前完成必要校验。
- 涉及用户、组织、Tenant、资源所有权时必须显式做权限与隔离检查。每个调用方只获得完成工作需要的最小权限。
- Secret、Credential、Token 不得硬编码、提交到仓库或写入日志。
- 下载、上传、查询、修改外部资源前必须确认调用者有权访问目标资源。
- 下级规则不得削弱安全底线。

## 10. 变更原则

- 一个 Issue 只完成一件事，并有一个主要 Owner。跨领域需求拆成多个 Issue；普通重构不得顺便改变公开接口、数据和业务规则。
- 小步变更，保持每一步可理解、可审查、可测试。
- 不为未来尚未出现的复杂度提前造目录、crate、接口或抽象。
- 修改领域边界、数据 Ownership、公开契约或跨模块依赖时，必须明确影响范围。
- 重构不得借机偷偷改变业务语义；业务变化和结构变化尽量分开。
- 发现同一规则在两三个真实位置重复后，再提取到最近共同上级或可复用规则。
- 下级规则可以补充和收紧，但不能静默覆盖或削弱上级规则。

### 开工前置条件

任何代码修改开始前，必须先完成本 Issue 的 Task Contract。没有 Task Contract，不得开始编码。

Task Contract 至少包含：

1. **ASCII 决策流程图（ASCII Decision Flowchart）**：编码前必须先画出本次变更的主执行链、关键调用关系、条件分支、失败路径和影响范围。禁止使用 Mermaid，统一使用纯文本，并使用 `↓`、`→`、`├─`、`└─` 表达执行顺序和条件分支。流程图必须让人在阅读代码之前看清楚程序从哪里进入、经过哪里、在哪里分支、最终到哪里。
2. **BDD / Acceptance Criteria**：写清楚本次必须实现的行为、验收条件和完成条件。验收条件只描述当前 Issue，不得把新发现的问题继续并入。
3. **Paths**：明确本次允许和禁止修改的代码范围。

其中 Paths 必须明确：

- **Allowed Paths**：可以修改的目录；
- **Conditional Paths**：说明理由并获得对应 Owner 同意后才能修改的目录；
- **Forbidden Paths**：当前 Issue 禁止修改的目录；
- **Protected Zone**：路由核心、认证核心、公开契约、账务核心、迁移历史等需要独立变更的区域。

### 编码与收口

编码只能围绕 Task Contract 中已经定义的目标、行为和路径进行。

- 发现与当前验收条件无关的问题，只记录或另开 Issue，不得顺手修复、重构、清理或扩展。
- 需要增加新的验收行为、修改新的目录或触碰新的 Owner 时，必须先停止当前实现，更新或拆分 Issue 后再继续。
- BDD / Acceptance Criteria 全部满足、相关测试通过且实际修改未超出 Paths 后，当前 Issue 即完成，必须停止。
- 完成条件满足后，不得因为“顺便优化”“以后可能需要”或“代码可以更漂亮”继续扩大修改。

出现以下情况必须停止并拆分或升级 Issue：需要跨领域修改内部代码、需要改变公开契约、需要修改其他 Owner 的业务真相，或者需要触碰未授权的 Protected Zone。

## 每个 crate 必须回答的问题

1. Owner 是谁？这个 crate 负责什么？
2. 不负责什么？拥有哪些业务真相和数据？
3. 对外提供哪些公开契约？
4. 可以依赖谁？谁可以依赖它？
5. 禁止哪些依赖、访问和越界行为？
6. 目录和文件怎样组织？
7. 代码应该怎样写？有哪些特殊错误、日志和安全要求？
8. 继承哪些上级规则和可复用规则？
9. 有哪些独有测试、状态、失败和迁移要求？
10. 完整正确示例和完整错误示例是什么？

已经由上级回答的内容，直接引用，不再复制。

## 最终检查

提交代码前至少能回答：

```text
它属于谁？
它负责什么、不负责什么？
它依赖谁，依赖的是不是公开边界？
它有没有碰别人的数据或内部实现？
失败、安全和测试是否被考虑？
这次变更有没有引入不必要的抽象？
```
